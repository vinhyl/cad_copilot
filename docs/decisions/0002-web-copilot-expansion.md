## 1. 背景与总体判断

cad_tools v0.1.1 已具备：OCP 几何内核封装（读 / 属性 / mesh 单一实现）、特征分类与拾取
（feature_locator / feature_picker）、MCP 8 工具（docstring 即 Agent 契约）、安全加固
（路径白名单、build123d 默认禁用、XSS 转义、vendor SHA-256 校验）、46 个 pytest 用例 +
三平台 CI 矩阵。

设想文档规划了 8 模块 Web Copilot。对照盘点的核心判断：

> **这个扩展的本质是给现有几何引擎"长出服务和前端"，而不是造一个新系统。**
> 设想中最难自研的部分（OCP 内核、特征拾取、Agent 工具化）恰是已完成的资产；
> 真正的跨越只有一个——运行模型从"批处理工具生成静态 HTML"换成
> "长驻服务 + WebSocket 双向通信"。所有规划围绕这一转变做增量演进。

模块支撑度盘点（现有代码可直接复用程度，0–5）：

| 设想模块 | 现有资产 | 主要缺口 | 支撑度 |
|---|---|---|---|
| 双视口联动 | three.js 离线 3D 预览 | 2D 渲染与对照交互 | 2/5 |
| 装配解耦·爆炸图 | 装配体判定（是/否） | 装配树、4×4 矩阵、实例化 | 1/5 |
| 自然语言意图映射 | MCP 8 工具 + 契约文档 | 意图解析、标准件选型库 | 3/5 |
| 拾取·修改·DFM | 特征分类拾取 + 4 种编辑 | 干涉检测、DFM 规则、Diff | **4/5** |
| 接口锁定 | — | 配合面识别全部新建 | 0/5 |
| DWG 校准·物性 | 体积/面积/质心/包围盒 | ezdxf/ODA、材质、内腔容积 | 2/5 |
| 一键设计体检 | — | 审查规则引擎与报告 | 0/5 |
| 渲染·动画 | STL 网格导出 | Blender/FreeCAD headless | 1/5 |

结论：**模块四是最佳切入点**（"点选→修改"闭环原型已存在）；模块五/七依赖模块二
（装配体解析）先行，不能 8 模块并行铺开；几何底座（cad_core 无环 DAG 分层）全部复用。

> **复审注（2026-08-19）**：模块四 4/5 的评估未计入 R1（特征身份稳定性）——现有
> fillet / chamfer 是对全实体所有边的钝操作，"点选哪个特征就改哪个特征"的**定点
> 编辑尚不存在**，是 Phase A/B 之间必须补的硬缺口（详见文末风险登记 R1）。

## D1 演进策略：增量演进 + 四阶段路线

**背景**：8 模块并行推进对个人/小团队不可行；审计确认核心架构质量良好，无重写必要。

**决策**：以现有 cad_core / feature_locator / feature_picker / cad_mcp_server 为底座增量
演进，按依赖链切四个阶段：

| 阶段 | 主题 | 关键交付 | 定位 |
|---|---|---|---|
| **A** | 服务化基座 | WebSocket 服务层、装配树 + 4×4 矩阵提取、前端 SPA 骨架、本地安全边界 | **关键转折点** |
| B | 查看体验闭环 | 3D 视口 + 装配树、爆炸图拖动条、拾取能力 API 化、glTF 实例化 | 先看得懂模型 |
| C | AI 修改闭环 | 自然语言修改、干涉检测护栏、DFM 成本预警、增量版本 Diff | 改得准、可撤销 |
| D | 增值能力插件 | DXF/DWG 校准、一键体检、FEA 求解、Blender 渲染 | 插件化可选 |

**理由**：装配体解析（设想模块二）是爆炸图 / 干涉 / 接口锁定 / Diff 的共同前置，
且其本身即可交付价值（Web 端流畅查看大装配体）。

**影响**：Phase A 是成败关键；Phase B 把 feature_picker 从"生成静态 HTML"改为
"WebSocket 查询返回特征几何"（拾取逻辑不动）；Phase C 时查看、拾取、版本管理就位，
AI 只需编排已有工具。

---

## D2 架构分层与通信

**背景**：设想中 "Codex / WorkBuddy / FastAPI" 并列含糊；Agent 生态与 Web 前端需要
同一套工具能力。

**决策**：

- 工具实现进一步下沉为**纯库层**（几何操作纯函数 + 明确的文件读写边界）；
- **同一套工具契约挂双 transport**：stdio 继续供 WorkBuddy 等 Agent 使用，
  WebSocket / HTTP 供浏览器前端使用；
- FastAPI / FastMCP 只做**确定性服务编排**；Agent 调度层复用 MCP 生态
  （Agent 客户端 + 工具服务共同构成设想中的"AI Agent 中枢"），**不自研 Agent 框架**。

**理由**：FastMCP 原生支持多 transport，无需推翻现有 server；避免 Agent API 与
Web API 双轨维护。

---

## D3 性能架构：Template + Matrix 解耦

**背景**：审计 M4 已证明"每特征 base64 嵌入 HTML"撑不住装配体规模（百级特征 →
数十 MB HTML，浏览器卡死）。

**决策**：坚持设想中的数据解耦设计并在 Phase A/B 优先落地——

- 装配体 STEP 拆解为**去重零件模板**（唯一 `.gltf` / `.step`）+ 各实例 **4×4 齐次
  变换矩阵 JSON**；
- Web 端同规格零件（如螺栓）只加载 1 次几何，GPU 实例化复制；
- 爆炸图 / 运动动画仅通过更新矩阵 JSON 实现，前端 60 FPS 无需重算几何。

**理由**：这是 glTF instancing 的标准做法，是设想中最值得坚持的设计。

---

## D4 2D/3D 交互：只做对照，不做特征级联动

**背景**：特征级 DWG↔STEP 语义映射（图纸视图 ↔ 模型面的对应）无通用解，属研究级
难题。主理人确认实际需求是"方便直观地跟 DWG 对照"。

**决策**：

- **同屏分栏 + 同步视角**：左 3D、右图纸（DWG→DXF→SVG），平移缩放按图纸比例联动；
- **零件级高亮**：点 3D 零件 → 高亮 2D 图纸同名实体 / BOM 序号（ezdxf 文本实体提取
  足以支撑）；
- **人工确认一次、永久记忆**：不确定的映射由用户首次手动点选，写入 `metadata.json`
  后自动生效——把"AI 自动解决语义映射"降级为"用户标注一次"；
- **特征级联动正式移出范围**。

---

## D5 DWG 依赖：默认开启 + 探测降级 + 缓存

**背景**：原分析建议"DXF 先行、DWG 后置"以规避 ODA File Converter（外部二进制 +
许可限制）的集成与分发风险。主理人确认：系统暂为团队本地自用，部署摩擦可接受，
DWG 默认开启。

**决策**：

- ODA File Converter **默认开启**；
- **启动探测 + 优雅降级**：服务启动时检测其存在，缺失时 DWG 功能报清晰提示而非
  崩溃，DXF（ezdxf 纯 Python）路径照常工作；
- **转换结果落缓存**（设想中的 `cache/dwg_converted.dxf`）：DWG→DXF 只转一次；
- **保留插件边界**：插件化的意义不是"默认关闭"，而是将来对外分发时一行配置即可
  关掉默认。

---

## D6 FreeCAD：子进程隔离的默认插件

**背景**：主理人质疑"FreeCAD 做可选是否合理，大部分功能都依赖它"。依赖面核实结论：

| 功能域 | 实际依赖 | 说明 |
|---|---|---|
| STEP 解析 / 布尔 / 干涉 / 物性 / DFM 几何检查 | **OCP（已有）** | 核心闭环完全不碰 FreeCAD |
| FEA 力学 / 热学 | FreeCAD + CalculiX | 设想中的唯一硬依赖 |
| 2D 工程图**生成** | FreeCAD TechDraw | 查看 DWG 不需要，仅"出图"需要 |
| 渲染 / 动画 | Blender | 与 FreeCAD 无关 |
| DWG 读取 | ODA + ezdxf | 与 FreeCAD 无关 |

即：**查看→拾取→修改→干涉→版本主干道是 OCP-only 的**，FreeCAD 只服务 FEA 与
出图两个支线。

**决策**：

- FreeCAD **默认开启**，但必须以 **headless 独立子进程**运行，主服务**永不
  `import FreeCAD`**；
- 理由：FreeCAD 自带整套 OCCT，与项目直接依赖的 `python-ocp` 同进程会产生
  DLL / 符号冲突（已知坑）；数据经文件或 RPC 交换；
- "默认开启的插件"成立——**关键是进程边界，不是开关状态**。

## D7 Blender / FEA：可选插件

Blender headless 渲染为可选插件；FEA 先做 CalculiX 静力学单场景（经 D6 的 FreeCAD
子进程），同为可选启用。核心链路保持**离线、轻依赖**，与项目现有定位一致。

> **落地注（2026-08-20）**：两插件的外层框架已实现（`cad_fea.py` /
> `cad_render.py` + `GET /api/plugins` / `POST /api/fea/static` /
> `POST /api/render`），采用**代码先行、依赖后装**策略：探测链（env → PATH →
> 常见安装路径）、结构化降级（缺依赖 → 503 + 安装提示）、内容寻址缓存（R8）
> 全部就绪并有测试覆盖（无依赖环境全绿）。**R5 任务协议已落地**：
> `cad_jobs.py` JobManager（job id + 进度 + 协作取消），`"async": true`
> 走 202 + `GET /api/jobs/{id}` 轮询 + `POST /api/jobs/{id}/cancel`；
> 子进程 Popen 化（terminate → 5s 宽限 → kill），FEA 进度直接中继内层
> 脚本各阶段 flush。前端含插件状态面板与任务进度卡片。内层 FreeCAD FEM /
> bpy 脚本按官方脚本 API 编写并带阶段进度汇报，**待安装依赖后首轮实跑
> 验证**（版本相关 API 漂移在该轮修正）。

## D8 AI 边界：意图解析 + 确定性工具编排

**决策**（延续项目既有哲学并扩展）：

- **严禁 AI 凭空估算物理数值**：所有物理计算（质量 / 重心 / 惯性矩 / 容积 / 应力）
  由后端确定性工具执行，AI 只解析意图、编排工具、解读结果；
- 接口锁定（设想模块五）不仅防用户误操作，**也防 AI 误改**：AI 修改后的确定性
  几何校验（干涉 / 拓扑有效）是每次写操作的**隐式护栏**，不是可选项；
- "docstring 即 Agent 契约"的规范延续到所有新工具。

## D9 Prompt 验证与固化：评测飞轮

**背景**：意图映射（设想模块三）依赖 LLM 能力而非工程能力，不确定性最高。主理人
确认：先不做 UI，但需要升级计划与验证方法。

**决策**：先跑"评测飞轮"，达标才固化交互，顺序不可反。

**① 基准集**（`evals/` 目录，版本化可回归，如 pytest）：

- 收集 30–50 条团队真实大白话指令（"把这根轴换个大号的"、"让这里更结实一点"）；
- 每条三层标注：**目标对象**（哪个零件/特征）、**黄金工具调用轨迹**（期望 MCP
  调用序列 + 参数）、**几何验收断言**（如孔径 M8→M10、体积变化范围）。

**② 批量评测**：复用现有 WorkBuddy + cad-engine MCP server，CLI 批量喂指令、
记录调用轨迹、跑几何断言。**不需要任何 UI，现在即可起步。**

**③ 归因迭代**，指标分四层、修复按层分流：

| 层 | 度量 | 修复手段 |
|---|---|---|
| 意图命中 | 选没选对目标对象 | 改 prompt / 补特征元数据 |
| 工具选择 | 调用序列对不对 | 改工具 docstring 契约 / 拆合工具粒度 |
| 参数正确 | 数值/单位/公差 | 改参数描述 / 加枚举约束 |
| 端到端 | 几何断言通过率 | 前三层综合结果 |

**④ 分级固化**（达标出口，非一刀切进 UI）：

- 高确定性指令类（如标准件选型，成功率 **≥95%**）→ 直接固化成下拉 / 卡片；
- 中确定性（结构修改类，**~90%**）→ AI 生成 2–3 个预设方案卡 + 二次确认；
- 低确定性 / 开放式 → 保留自然语言通道，不强行固化。

**CI 策略**：LLM 调用不进全量 CI（成本与波动），抽样 / 手动触发；几何断言部分
全量跑。固化后的交互回灌基准集成为 UI 回归测试，飞轮不退役。

**升级路径**：CLI 批量评测（现在）→ 聊天内结构化建议卡片（Phase C 初期）→
完整 UI 控件（Phase C 成熟期）。每步升级的门槛 = 上一轮的达标率。

## D10 图模一致性（Drawing-Model Associativity）

**背景**：修改 STEP 后若版本管理不携带对应 DWG，对照查看 / 语义校准 / 体检报告等
所有 DWG 下游功能都会拿过期图纸说谎。设想模块六定义"DWG 是语义真理"**仅在导入时
成立**；系统开始修改 STEP 后，真理方向翻转——STEP + 语义层必须反过来驱动 DWG 更新。

**决策**：

1. **双轨修改**：一次修改意图同时驱动两轨——几何轨改 STEP（孔 M8→M10），语义轨
   同步改 `metadata.json`（该孔记录 M8→M10）。AI 只编排意图，**两轨的 diff 与
   校验全部是确定性代码**。
2. **metadata.json 升级为版本化语义中枢**；DWG 更新由**新旧 metadata 的语义 diff**
   驱动（哪些标注受影响、值从多少变到多少可精确算出，不需要 AI 猜）。
3. **DWG 分级更新**：

   | 级别 | 适用场景 | 手段 | 自动化程度 |
   |---|---|---|---|
   | T1 标注改值 | 值变拓扑不变（M8→M10、厚度 2→3） | ezdxf 修改 DIMENSION 实体文本覆盖 | 全自动 |
   | T2 视图重建 | 拓扑变化（加筋、改轮廓） | OCP HLR（纯 OCP）或 FreeCAD TechDraw 子进程重建视图，标注按拓扑匹配继承 | 半自动，需复核 |
   | T3 人工复核 | 新特征需新标注、视图布局重排 | 标记 stale + UI 显式提示，人来了结 | 人工 |

   工程边界：T1 是确定性代码，T2 是"生成后必须过一致性检查"，T3 老实承认做不到
   （商用 CAD 改模型后图纸同样需人工检查标注附着，内部工具不追求超越此水平）。
4. **原子版本提交**：几何或图纸任一轨失败，整个版本不落盘，回滚到上一版本——
   宁可没有新版本，不可有静默不一致的版本。
5. **DWG staleness 状态机**：`fresh → stale（几何已改，图纸未更） → updated
   （T1/T2 完成） → verified（体检通过）`。任何 DWG 下游功能（对照查看 / 语义
   校准 / BOM）读取前先查状态，stale 显示警示；与 D5 的缓存机制天然融合。
6. **版本节点升级为"一致性文件族"**：`versions/v1.x/` 含 step / gltf / matrix +
   `metadata.json` + `drawing.dwg` + changelog；**历史版本 DWG 永不重写**。
7. **模块七双重角色**：设想中的"STEP↔DWG 不一致差异点检测"从一次性体检升级为
   **每次版本提交的守门检查**——语义 diff 算出的期望值 vs 实际 DWG 标注值，
   对不上拒绝提交。同一段代码，导入时做体检，提交时做哨兵。
8. **不变量**：任何版本节点中 DWG 与 STEP 要么一致、要么显式标记 stale，
   **禁止静默不一致**。

**设计收益**：DWG 更新挂在 metadata 语义层而非几何 diff 上，语义 diff 天然跨格式
——DWG 只是语义中枢的一个"投影"，将来 BOM 表 / 其他图纸格式从同一中枢取更新指令。

## 延续约束一：安全边界（服务化后同步升级）

保留 v0.1.0 已落地的全部安全机制，并叠加服务化新增项：

- **保留**：`CAD_MCP_ALLOWED_DIRS` 路径白名单、`build123d_model` 默认禁用 +
  超时沙箱子进程、HTML 生成统一转义、vendor SHA-256 校验（缺文件即报错不静默联网）；
- **新增**：Web 服务仅绑定 127.0.0.1、本地 token 鉴权、CORS 收紧。
- **演进（2026-08-20，输入通道决策）**：白名单语义 = "字符串路径尝试读"，
  只防意外不构成授权；用户亲手交付文件 = **显式授权**，语义不同——
  `POST /api/upload`（原始请求体流式落盘，文件名仅取 basename + 净化）与
  白名单并行，uploads 目录自动加入 allowed_dirs。上传**内容寻址**
  （`uploads/<sha256>/<文件名>`）：同一文件重复上传去重回路径（与 parse
  缓存同构），不同内容分目录（ODA 按整目录转换，DWG 不混放）。前端由此
  移除路径手输（上传 / 拖放 / 最近使用为唯一输入通道）；agent 预览走
  `/app?load=<encodeURIComponent(路径)>` 一次性 URL 参数，**路径仍受
  `safe_input_path` 权威校验**——agent 无法借该入口越权读白名单外文件
  （越权时 403 + 可操作文案）。

## 延续约束二：工程纪律

- 新模块一律"库层纯函数 + 薄服务层"；docstring 即契约；pytest 黄金断言 +
  三平台 CI 矩阵照旧；
- `workspace/versions/` 用 manifest（SQLite 或 JSON 索引）管理版本节点，
  避免目录扫描式版本管理的性能与一致性问题；
- 前端从 vendored three.js 单文件模式转为 Vite 构建 + 本地静态 serve
  （离线能力不受影响）；
- 关键决策落编号 ADR（本文件即 ADR-0002），与 ADR-0001 并列；设想原文迁入
  `docs/architecture/copilot-vision.md`（活文档，随实现演进）。
